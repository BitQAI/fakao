## 0. 结论摘要

1. 本工具的定位（AI 法考冲刺教练：动态排程 + 看背/听学/自测 + AI 报告答疑）在垂直工具里是有差异的：**多数法考 APP 强在题库/课程/社区，弱在"个人化记忆调度"；本工具正好反过来**，这是优势，应保持。
2. 对标行业后，本工具最值得补的三个能力：**错题本（法考 APP 标配）**、**记忆曲线/学习统计可视化（Anki/墨墨标配）**、**打卡/连胜激励（多邻国/墨墨标配）**——三者数据现成（`reviews`/`quiz_answers` 已全量记录），主要是视图与聚合问题，不改表结构即可落地。
3. 现有功能存在 **4 个口径/逻辑问题**（完成率只算看背、覆盖树与调度两套状态、听学"已听"判定过宽、Web 导入后条目不可见）和 **若干信息架构问题**（标记仅存本地、自测历史与看/听历史分散、听学剩余语义误导等），建议先修再扩。
4. 建议评审后按 P0（口径修正）→ P1（错题本/图表/打卡/模考）→ P2（AI 诊断/多端同步）推进；全部走 Spec → Plan → 逐 Task 执行 → e2e 验证流程。

### 1.3 对标差异总结

**本工具已有（对标不落后）**：间隔复习调度（动态容量 + 错题置顶）、听学磨耳朵（音频队列 + 续批生成）、AI 答疑、自定义组卷（科目/考点范围）、覆盖树监控、早/晚报复盘。

**本工具缺失（行业标配）**：错题本独立视图、记忆曲线/学习图表、打卡/连胜激励、限时模考/智能组卷题量控制、标记/收藏跨设备同步、AI 个性化诊断。

## 3. 冗余与需调整问题（按严重度排序）

### 3.1 P0 —— 统计口径与功能缺陷（先修）

**① 完成率只算看背，与用户感知严重不符**
`today_stats.done` 只统计 `mode='read'`（`service.py`），自测、听学一律不计入；页面却显示"已完成 x/y"。用户听 10 段、做 10 题后完成率仍为 0%，误导性强。
建议：`done = read + quiz`（自测计入），听学单独展示分钟数（已有 `listen_min`），文案改为"看背+自测 x/y · 听学 z 分钟"。

**② 覆盖树与调度是两套状态逻辑**
`coverage.entry_state` 用 `last_result + review_count` 判定 new/learned/weak/mastered；`scheduler.classify` 用 `last_result + 天数 + 是否 quiz 错过` 判定 retry/review/new。后果：**quiz 答错的条目在覆盖树里仍显示"已学"（非薄弱）**，用户看到的"薄弱"与调度里的"错题置顶"对不上。
建议：覆盖树状态统一以调度为准（weak ⇐ retry 桶；未学 ⇐ 无 read+listen+quiz 有效记录），或至少把 quiz 错题并入 weak。

**③ 听学"已听"判定过宽**
暂停≥15 秒、播完、**手动跳过**三路都写 `result=exposed`。用户点开音频 3 秒后点跳过，也计入"已听"，条目从"未听池"消失，影响续批与覆盖判断。
建议：跳过不再直接计已听，或统一以 `duration_sec` 为门槛（如 ≥10s 才算暴露）；"点开未听"与"听过"分开语义。

**④ 设置页"数据导入"导入后条目不可见**
`importer.py` 默认 `status=draft`，全库查询都过滤 `status='final'`（AGENTS.md 铁律 1）。Web 导入后用户看到"导入成功 N 条"但列表为空——功能实际不可用。
建议：Web 导入接口导入后自动 promote 为 final（与 `import_entries.py` + 手动 UPDATE 流程一致），或明确标注"仅开发者使用 + 提示后续步骤"。

### 3.2 P1 —— 信息架构与体验问题

**⑤ 听学标记仅存 localStorage**
`progressStore.ts` 的标记条目是设备级的，清缓存/换设备即丢；且"标记"与 retry 桶、错题本职责重叠（标记想重背的 → 本质是错题/收藏）。建议服务端化（新 `marks` 表）或明确为"临时收藏"。

**⑥ 自测历史与看/听历史分散**
报告页"历史"只有看/听；做题记录藏在自测 tab 内。复盘页看不到"今天错了几题、错在哪"，与"报告"的定位不符。建议把 quiz 历史并入报告页历史，或复盘页加错题摘要。

**⑦ 听学"剩余可听 X"语义误导**
`queue.remaining` 是**全库未听总数**（`_listen_pool` 的 remaining 不考虑 exclude），但页面文案是"剩余可听"；`listen_more` 返回的 remaining 同样未排除当前队列，与 custom 接口（exclude 后计数）口径不一致。
建议：统一为"当前队列外可听数"或改文案为"未听总数 X · 本轮剩余 N"。

**⑧ 排行榜命名与口径**
"排行"实为**条目重复学习排行**（重复次数 = 次数-1），不是用户排行。名字易误解；"听 2 次 = 重复 1 次"的口径也容易引起疑问。建议改名（如"高频条目"）或副标题说明口径。

**⑨ 看背"上一个"重复评分无提示**
返回上一张可再次评分，重复写 `reviews`（排行榜重复次数由此产生）；"今日已看"有服务端 `reviewed_today` 与前端本地 `Set` 双源。建议：已评过分的卡片返回时提示或禁用评分，双源合并为单源。

**⑩ 早/晚报依赖 LLM，费用与延迟**
每日各生成一次（已有缓存），无 key 时走规则兜底（`ai.py` 设计如此）。建议确认兜底文案质量；若 key 欠费（AGENTS.md 铁律 4），报告页"生成晚报"会直接失败，需优雅提示。

### 3.3 P2 —— 技术债

**⑪ 文件行数逼近硬上限**：`service.py` 491/500、`ListenView.tsx` 433/500、`FlashcardView.tsx` 353/500。继续加功能前先按职责拆分（听学/计划模块、hooks）。
**⑫ 队列位置恢复逻辑脆弱**：localStorage 公共前缀匹配，计划一变即回退。建议服务端记"上次学习位置"或按 `reviewed_today` 锚点。
**⑬ SQL 模式重复**：多处手拼 `IN (?,?)` 占位符，可抽 helper（小成本）。
**⑭ 无固化 e2e**：之前用 Playwright 人工验证过，仓库内无 e2e 脚本/测试。建议本轮起固化 `playwright` 用例（看背/听学/自测/报告主链路）。
