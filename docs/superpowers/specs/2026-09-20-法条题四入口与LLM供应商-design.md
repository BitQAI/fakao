# 法条驱动题四入口覆盖 + LLM 供应商切换 — Spec（2026-09-20）

## 1. 背景与用户要求

1. **自测、看背、听学三个入口都要完整覆盖法条驱动题**，另外**法条页要挂题**。
   现状：12052 道法条驱动客观题**只有「组卷」一个入口**（每 3 题留 1 题），
   今日自测 10 题实测全是条目题，看背/听学是纯条目（卡片 + 音频），法条页只读。
2. **所有需要 LLM 生成的地方优先使用 opencode 的 `deepseek-v4.1-flash`**，
   阿里云 TTS 不变。

## 2. 现状与约束（实测）

| 事项 | 实测结果 |
|---|---|
| opencode 通道 | `POST https://opencode.ai/zen/go/v1/chat/completions`，需 `x-opencode-session` 头，否则 400 `MissingSessionID` |
| 模型特性 | **推理模型**：同题消耗 431 reasoning tokens；`max_tokens=64/256` 时返回**空串**（预算被推理吃光），1600 才稳定出 JSON |
| 性能对比 | opencode 4.6s/次 vs deepseek-chat 1.2s/次（同一出题提示词） |
| 现有入口 | 自测=`build_daily_quiz`（只从条目选题）；看背=`plans/*`+`entries`；听学=`_listen_pool`（`reviews JOIN entries`）；法条页=`statute_index` 只读 |
| 数据现状 | 法条驱动客观题 12052（`origin='bank'`、`entry_id IS NULL`），判断题 1510（已发布） |

## 3. 方案概要

### 3.1 LLM 供应商链（`app/ai.py`）

- 供应商顺序由 `LLM_PROVIDER_ORDER`（默认 `opencode,deepseek`）决定，只启用配置了 key 的供应商。
- opencode 供应商：带 `x-opencode-session` 头；`max_tokens` 自动加推理预算
  （`max(请求值, OPENCODE_MIN_MAX_TOKENS=1600)`）；**返回空串视为失败**，自动落到下一家。
- DeepSeek 供应商：行为不变（无推理预算、无额外头）。
- 密钥只放仓库根 `.env`：`OPENCODE_API_KEY` / `OPENCODE_BASE_URL` / `OPENCODE_MODEL`（已写入，未提交）。
- 可观测：`ai.provider_status()` 返回各供应商是否启用与最近一次调用命中的供应商，供排障。

### 3.2 统一抽象：法条卡（statute card）

> 一个法条卡 = 一条法条 + 基于它命制的客观题/判断题（1..n）。

- 数据来源：`quizzes` 中 `entry_id IS NULL AND basis != '' AND status='published'`，
  按 `statutes.resolve_law_article(basis)` 归到 `(法条库主名, 条号, 子条号)`。
- 卡片正/背面：正面=题干（选择题四选项 / 判断题」，背面=正确答案 + 解析 + 依据 + 条文原文摘要。
- 已看/未看：新增轻量表 `card_seen(card_key TEXT PRIMARY KEY, ts TEXT, mode TEXT)`，
  `card_key = "q:<quiz_id>"`。用于「优先未看过」轮转，保证长期可穷尽全部法条题。
  （不改 `reviews`：它有 `entry_id NOT NULL` 外键，法条题没有条目。）

### 3.3 四个入口

| 入口 | 覆盖方式 | 记录 |
|---|---|---|
| 自测（今日） | `build_daily_quiz` 每 3 题留 1 题给法条驱动题（与组卷同规则），未练过优先 | `quiz_answers`（正常作答） |
| 看背 | 队列 = 条目卡 + 法条卡（每 3 张留 1 张），题卡翻面可评分 | `card_seen(mode='read')` |
| 听学 | 队列 = 条目音频 + 法条卡音频（每 3 条留 1 条）；音频文本=依据+文摘要+题干+答案+解析，按 `data/audio/q<quiz_id>.wav` 缓存 | `card_seen(mode='listen')` |
| 法条页 | 条文下挂「练这一条（N 题）」，可就地作答 | `quiz_answers` |

**「完整覆盖」的可验证定义**：对入口 E 的候选池 P(E)，要求
P(E) ⊇ 全部法条驱动的已发布题（`entry_id IS NULL`）；且轮转算法保证连续取队列 N 次
（N 为题库题量/每次配额）能把 P(E) 取尽（无重复卡死、无遗漏）。用单测 + 审计脚本验证。

### 3.4 听学音频成本控制（重要）

法条卡 12052 道，每道音频文本 ~150-200 字（约 25-35 秒语音），全量合成属大额支出。
方案：**按需续批**——进入听学池时只合成「队列内缺音频」的卡，单次批量上限
`LISTEN_QUIZ_BATCH`（默认 10），失败重试沿用现有 TTS 链路；已合成即命中缓存不再重复计费。
用户可随时调整批量或暂停（把该值设为 0 即关闭法条卡音频，队列自动只出条目卡）。

## 4. 非目标

- 不把法条题写进 `entries`（保持「条目=知识卡、题库=练习」两层结构）。
- 不导出做题历史/看卡记录（`card_seen` 是本地进度）。
- 不改阿里云 TTS 配置与语音（仍 `qwen-tts` + Ethan）。
- 不为法条卡做「错题本」以外的统计改造（错题本已按 `quiz_answers` 工作）。

## 5. 验证标准

1. `pytest` 全绿；新增供应商链、法条卡池、四入口配额与轮转的单测。
2. 入口覆盖审计：四个入口的候选池各自 ⊇ 全部 12052 道法条题，且模拟连续取队列可穷尽。
3. Playwright 实测：自测混入法条题、看背出现题卡并可翻面评分、听学出现法条卡音频、
   法条页可就地作答。
4. `tsc`/`eslint` 无告警；`audit_quiz_coverage.py` 覆盖率不下降（仍是 86.1%）。

## 6. 风险

| 风险 | 对策 |
|---|---|
| opencode 推理模型空响应/超时 | 空串与异常一律视为失败并回落 DeepSeek；批量脚本可中断续跑 |
| 批量生成变慢（4x） | 只在大批量离线任务使用；在线交互（AI 问答）保持短 prompt |
| 听学音频支出失控 | 默认按需 + 单次批量上限 + 可一键关闭 |
| 看背/听学混入题卡打扰背诵节奏 | 题卡按 1/3 配额且排在条目卡之后；可再加开关 |

## 7. 实测结果（2026-09-20 实施后）

| 验收项 | 结果 |
|---|---|
| LLM 供应商链 | `provider_status()` 实测 `last_used=opencode`；空响应/异常自动回落 DeepSeek |
| 自测 | 今日 10 题 = 7 条目题 + 3 法条题；法条判断题按「对/错」作答并服务端判分 |
| 看背 | 条目卡看完后出现「法条题卡 1/3」，作答回显解析与条文 |
| 听学 | 每听 3 段插入 1 张题卡（队列自动续批，排到队尾不可行），音频按需合成 |
| 法条页 | 条文展开显示「练这一条（N 题）」，就地作答 |
| 入口覆盖审计 | 四个入口各 **13160 / 13160**，缺口 0 |
| 回归 | `pytest` 419 passed；`tsc` / `eslint` 无告警 |

补充决策（与实现一致）：

- 「今日自测」的科目偏好改为**排序偏好**而非硬过滤，否则单日科目会锁死覆盖。
- 听学卡片音频成本随「实际听到的卡」增长（`/api/audio/card/<quiz_id>` 命中缓存不重复合成）。
- 判断题库（数判）与法条卡池有重叠：数判按 `judge` 题库抽题，法条卡池按「题是否挂在法条上」抽题，
  两者互不影响，都会推进 `card_seen` 的对应 mode。
