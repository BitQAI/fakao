# Spec：条目长度硬限制移除 · 存量截断修复 · TTS 法条先行

日期：2026-09-15

## 1. 问题背景

条目生成链路对四个字段做了字数硬限制（`backend/app/importer.py` 第 14-18 行），
并在生成后由 `backend/scripts/generate_entries.py` 的 `fix_anchor` / `fix_conclusion` /
`fix_tts` 按字符硬切。全库 2426 条实测后果：

| 现象 | 数量 | 证据 |
|---|---|---|
| 结论句被切成半截 | 31 条 | `SG-067` 结尾「不能协议排除（民诉法第2。」（法条号断在「第2」） |
| TTS 文本被硬切 | 3 条 | `MF-114` 结尾「依据《民法典婚姻家庭编解释（二」（括号未闭合） |
| anchor 疑似被截断 | 463 条 | `SG-040` 结尾「收养人和被收养人经常居」（词被切断） |
| point 越界未被拦截 | 7 条 | `SG-226` 20 字「行为地与结果地分离时适用有利于被侵权人法」，仅提示词约束 |

根因：`fix_*` 采用「先按字数硬切、再补标点」策略，切断位置与语义/法条号边界无关；
`validate_entry` 用同一条字数字线兜底，导致 LLM 输出稍长即被整批拒绝或静默削足。

## 2. 目标

1. anchor 目标上限由 36 字放宽到 42 字。
2. 移除 point / conclusion / anchor / tts_text 的字数硬校验与字数硬截断，字数只在提示词中
   作为「建议范围，必要时可越界」表达。
3. 修复存量被切断的字段（conclusion / tts_text 必做，anchor 视确认结果）。
4. 新增/重写条目时，TTS 文本采用「法条先行」结构。

## 3. 非目标

- 不改数据库 schema、不改 Alembic 迁移（本次不触及 models/枚举/索引/约束）。
- 不做全库 1732 条「有 statutes 条目」的批量 TTS 改写（见第 7 节待确认项）。
- 不改前端展示逻辑（前端无字数截断/line-clamp，仅展示层不受影响）。
- 不重写未受损条目。

## 4. 方案设计

### 4.1 校验层 `backend/app/importer.py`

- 删除 `ANCHOR_MIN/ANCHOR_MAX`、`CONCLUSION_MAX`、`TTS_TEXT_MAX` 四个长度常量及
  `validate_entry` 中对应断言。
- 保留（非字数类校验）：必填字段、ID 格式、priority 枚举、cases ≤3 且来源合法、
  sources ≥1 条且含 `type/ref/loc`。
- conclusion「以句号结尾」暂作保留项（它是标点格式而非字数限制，且音频/展示依赖断句），
  是否一并放宽见第 7 节待确认项。

### 4.2 生成层 `backend/scripts/generate_entries.py`

- `_build_prompt` 约束文案改为"建议范围 + 可越界"：
  - `point` 建议 ≤15 字
  - `anchor` 建议 16-42 字
  - `conclusion` 建议 ≤60 字
  - `tts_text` 建议 ≤150 字
  - 明确「以上为建议区间，语义完整性优先，必要时可越界，不要为凑字数删减法条号或断句」
- `fix_anchor`：去掉 36 字截断，仅 `strip`；超过 42 字打印 WARN（可观测，不阻断）。
- `fix_conclusion`：去掉 59 字截断，仅补句号/规整结尾标点。
- `fix_tts`：去掉 150 字截断，仅 `strip`。
- 新增：三个 `fix_*` 的超长 WARN 汇总进 `generate()` 的 stats（便于后续人工复查）。

### 4.3 TTS 法条先行规则（生成提示词）

`tts_text` 结构改为：

```
【科目·考点】<场景一句话>。<若有明确法条适用>依照/依据 <法条简称>第N条[、第M条]规定，<结论>。<否则><结论>。
```

约束：

- 仅当条目 `statutes` 非空且资料中确有该法条适用时采用法条先行，避免生搬。
- 多条并列写法：`依照刑诉法第192条、第193条规定，……构成XX罪。`
- TTS 是要朗读的文本，**禁止 Markdown 标记（反引号/星号）**，法条名用简称（刑诉法、民法典、
  公司法…）+ 条号。
- 无明确法条适用时保持「场景。结论。」，不强行插入法条。

### 4.4 存量修复 `backend/scripts/fix_truncated_entries.py`（新增）

职责：扫描 `data/entries/*.json`，定位受损字段，调 DeepSeek 补全，写回 JSON。

- **候选识别（启发式，保守）**
  - conclusion：括号 `（）/《》/“”` 不配对；结尾匹配 `第[数字]。$`；长度 ≥58 且末句疑似中断
  - tts_text：括号不配对；长度 ≥148
  - anchor：长度 ≥34 且结尾为 `，、；` 或疑似断词（`--with-anchor` 显式开启，默认只报不修）
- **修复方式**：按批（默认 10 条/批）把 `point / anchor / 受损字段原文 / sources.loc 原文 /
  statutes` 交给 DeepSeek，要求「只补全被切断处，不新增原文没有的结论，法条号必须完整且与
  statutes 一致，TTS 顺带改为法条先行」。模型对未受损项返回 null，避免误改。
- **核验**：修复后新文本必须满足 ①法条号完整（`第N条`，不出现 `第N。`）②括号配对 ③长度记录
  ④若 sources.loc 存在，新文本的关键结论词需能追溯到原文或 stats。人工抽检 10 条。
- **开关**：`--dry-run`（默认扫描出清单）、`--only=conclusion,tts`、`--subject=`、`--id=`、`--batch=`。

### 4.5 落库与音频

1. 修复后的 `data/entries/<科目>.json` → `scripts/import_entries.py`（校验 errors=0）
2. `UPDATE entries SET status='final' WHERE status='draft'`（铁律 1）
3. 仅对 tts_text 发生变化的条目删除 `data/audio/<id>.wav` → `scripts/synthesize_audio.py`
   （音频缓存只看文件是否存在，不比对文本，不删不会重生成）

## 5. 数据模型与接口

无变更。`entries` 表字段不变，无迁移，无 API 变更。

## 6. 验证标准

1. `pytest` 全绿（新增：超长 anchor/conclusion/tts 通过 `validate_entry`；`fix_*` 不再截断）。
2. `fix_truncated_entries.py --dry-run` 输出的受损条数在修复后归零（同一启发式复扫）。
3. 全库复查：`第N。` 截断模式 0 条、括号不配对 0 条、TTS 无 Markdown 标记。
4. 修复条目 `import_entries.py` errors=0，`status='final'` 计数不低于修复前。
5. 变化条目的 wav 重新合成成功，`/api/entries/<id>` 的 tts_text 与音频一致（抽听 3 条）。

## 7. 待确认项（阻塞执行的部分）

1. **存量 TTS 法条先行的范围**：仅修复受损条目（约 34 条），还是对全库有 `statutes` 的 1732 条
   批量改写（需 1732 次 DeepSeek + 1732 次 DashScope 合成，成本与耗时显著）？
2. **conclusion 是否也法条先行**：当前设计只在 tts_text 用法条先行，conclusion 保持既有写法。
3. **conclusion「以句号结尾」是否保留为硬校验**（非字数限制）。
4. **anchor 是否纳入修复**（463 条候选，需额外约 47 次 LLM 调用）。

## 8. 风险

- LLM 补全可能引入原文未支持的结论 → 以 sources.loc 原文 + 人工抽检兜底，修复脚本保留
  `--dry-run` 与逐条 diff 输出。
- 去掉字数上限后新增条目可能出现超长文本 → 用 WARN 观测，配合 `fix_*` 的句边界策略与人工
  复查，不引入新的硬阈值。
- 音频重合成需要 DashScope 余额，欠费会失败（属外部阻塞，先探测再批量跑）。
